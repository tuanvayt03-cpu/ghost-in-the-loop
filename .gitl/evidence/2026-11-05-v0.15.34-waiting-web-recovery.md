# Ghost+ v0.15.34 — waiting/web-recovery false HUMAN repair — 2026-11-05

## Symptom
On a long-running task that was intentionally waiting/polling (for example a GitHub Actions build/render), Ghost+ 0.15.33 could enter:
- PAUSED · HUMAN_REQUIRED
- reason: "Status probe không được xác nhận và không đủ bằng chứng chứng minh send FAILED..."

The task did not actually require a human decision.

## Root causes
1. Web Recovery captured Ghost Play before clicking Ghost Stop.
   Stop re-renders #gitl9, detaching the captured Play node.
2. Web Recovery staged a raw recovery probe, but Ghost Core owns Send and wraps that draft with bootstrapPrompt(...) before dispatch.
   Web Recovery independently waited for the raw staged prompt receipt, so a successful Core send could not satisfy its own receipt matcher.

## Repair
- Re-acquire the live Play control only after Stop, probe staging and final host Send-control confirmation.
- If the fresh Play control is unavailable before Send, clear only the exact managed draft and keep monitoring instead of raising HUMAN_REQUIRED.
- Record the Core round at the start of a recovery attempt.
- Treat Core round advancement as authoritative recovery acceptance because Core increments round only after its own independent matching-user-turn receipt succeeds.
- Retain the exact raw user-message receipt as a conservative fallback for any future direct-send implementation.
- Runtime version bumped to 0.15.34.
- Loader version bumped to 9.0.0-alpha.2+ghostplus.15.34.
- Immutable runtime-manager and web-recovery pins target source checkpoint:
  d6b7be3505d16a81d537bf68e490facb00e48651

## Regression
